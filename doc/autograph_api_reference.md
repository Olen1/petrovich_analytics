## 1. Как устроен API

AutoGRAPH.NET — система спутникового мониторинга транспорта. Её HTTP-интерфейс построен по схеме
«одна операция — один URL», без REST-ресурсов: метод указывается прямо в пути, все данные передаются
параметрами. Адрес любого вызова выглядит так:

```
https://web.tk-ekat.ru/ServiceJSON/<ИмяМетода>?session=<токен>&schemaID=<GUID>&...
```

### 1.1. Транспорт и методы HTTP

Почти все операции доступны и как `GET`, и как `POST` — с одним и тем же набором параметров:

| Способ вызова | Количество методов | Комментарий |
|---|---:|---|
| `GET` и `POST` | 113 | параметры в query string либо в теле |
| только `POST` | 71 | изменяющие операции и методы с большим телом запроса |
| только `GET` | 8 | чтение профилей и настроек UID |

Для `POST` сервис принимает `application/x-www-form-urlencoded`, `application/json`, а для методов
с табличными свойствами и файлами — `multipart/form-data`.

> **Практическое правило:** для чтения используйте `GET` — его проще отлаживать и кэшировать.
> Для записи и для запросов с длинными списками ID используйте `POST`: длина query string ограничена
> сервером, а список из сотен GUID'ов легко её переполняет.

### 1.2. Авторизация

1. Вызовите `Login` с логином и паролем — получите строку-токен.
2. Подставляйте этот токен в параметр `session` во всех остальных вызовах.

Если `session` отсутствует или недействителен, сервис отвечает **HTTP 401** с пустым телом —
никакого JSON с описанием ошибки не возвращается. Это проверено на живом сервисе:

```
GET /ServiceJSON/EnumSchemas   →   401, тело пустое
```

Схема ошибок в API минималистичная: 185 методов из 192 декларируют единственный ответ `200`,
пять методов работы с разрешёнными UID могут вернуть `400`. Отдельного формата тела ошибки нет,
поэтому клиент должен ориентироваться на HTTP-код и на пустой/непустой ответ.

### 1.3. Организация (схема) — обязательный контекст

Почти каждый метод требует `schemaID` — идентификатор организации (в терминах системы — «схемы»).
Получить его можно методом `EnumSchemas`. Идентификатор присваивается схеме при создании
и никогда не меняется, поэтому его можно кэшировать на стороне клиента навсегда.

Из 192 методов:

* `session` требуют **191** (все, кроме `Login`);
* `schemaID` требуют **154**; остальные работают на уровне сервера или группы организаций
  (`EnumSchemas`, `EnumOrgs`, `EnumRoles`, управление группами организаций, разрешённые UID).

### 1.4. Время и часовые пояса

`Login` принимает необязательный параметр `UTCOffset` — смещение в минутах. Он задаётся один раз
на сессию и определяет, в каком поясе сервис интерпретирует входные даты и возвращает выходные.

| Где | Формат | Пояс |
|---|---|---|
| `SD` / `ED` в методах данных и отчётов | `yyyyMMdd` или `yyyyMMdd-HHmm` | с учётом `UTCOffset` |
| `SD` / `ED` в свойствах (`SetProperties`) | `YYYY-MM-DD HH:mm:ss` | **без** учёта `UTCOffset` |
| `SD` / `ED` в табличных свойствах | `yyyy-MM-ddTHH:mm:ss` (ISO) | **без** учёта `UTCOffset` |
| Биллинг (`dtUtc`, `sdUTC`, `edUTC`) | `yyyyMMdd` или `yyyyMMdd-HHmm` | **всегда UTC** |
| `at` в методах чтения свойств | дата-время | **UTC** |

> Это самый частый источник ошибок при интеграции: три группы методов используют три разные
> трактовки времени. При разборе ответов обращайте внимание на пары полей `SD`/`SDLocal`
> и `DT`/`DTLocal` — сервис отдаёт и UTC-, и локальное значение.

### 1.5. Идентификаторы и списки

Идентификаторы объектов — GUID. Там, где параметр называется `IDs` (множественное число) и имеет
тип `string`, значения перечисляются **через запятую** в одной строке:

```
IDs=8f2c...a1,3b7d...e9,0c44...77
```

Часть административных методов вместо этого принимает настоящий массив (`ids`, `uids`, `orgIds`) —
в этом случае в JSON-теле передаётся массив, а не строка.

### 1.6. Иерархия объектов

Методы `EnumDevices`, `EnumDrivers`, `EnumGeoFences`, `EnumImplements`, `EnumTasks` возвращают
плоские списки: `Groups` (группы) и `Items` (объекты). Дерево собирается на клиенте сопоставлением
`ID` ⇔ `ParentID`; корневые элементы имеют `ParentID = null`.

Поверх реальной иерархии существуют **виртуальные деревья** — произвольные пользовательские
группировки тех же объектов (раздел «Виртуальные деревья»). Они возвращаются в тех же ответах
в поле `VirtualTrees`, а активное для пользователя дерево — в `VirtualTreeAssigned`.

## 2. Быстрый старт

```bash
# 1. Получить токен
curl -s "https://web.tk-ekat.ru/ServiceJSON/Login?UserName=USER&Password=PASS&UTCOffset=300"
# → "6f1c2b90-...-a13f"   (строка-токен)

# 2. Узнать доступные организации (схемы)
curl -s "https://web.tk-ekat.ru/ServiceJSON/EnumSchemas?session=TOKEN"
# → [{"ID":"...","Name":"ООО Ромашка","Group":null,"GroupID":null,"State":true}]

# 3. Получить дерево техники
curl -s "https://web.tk-ekat.ru/ServiceJSON/EnumDevices?session=TOKEN&schemaID=SCHEMA"
# → {"ID":"...","Groups":[...],"Items":[{"ID":"...","Name":"КАМАЗ 001","Serial":123456,...}]}

# 4. Текущее положение
curl -s "https://web.tk-ekat.ru/ServiceJSON/GetOnlineInfo?session=TOKEN&schemaID=SCHEMA&IDs=DEV1,DEV2"

# 5. Рейсы за сутки
curl -s "https://web.tk-ekat.ru/ServiceJSON/GetTrips?session=TOKEN&schemaID=SCHEMA\
&IDs=DEV1&SD=20260820&ED=20260821"
```

Типовой сценарий интеграции: `Login` → `EnumSchemas` → `EnumDevices` → далее методы раздела
«Получение данных по приборам». Токен и `schemaID` кэшируются, дерево техники перечитывается
по изменению, данные запрашиваются по расписанию.

## 3. Выбор метода получения данных

Раздел «Получение данных по приборам» содержит 20 методов, и разница между ними неочевидна.
Ориентир:

| Задача | Метод | Что вернёт |
|---|---|---|
| Где машина прямо сейчас | `GetOnlineInfo` / `GetOnlineInfoAll` | последняя точка, скорость, курс, адрес, финальные параметры |
| Линия трека на карте | `GetTrack` | массивы `DT`, `Lat`, `Lng`, `Speed` по индексам |
| Раскраска трека по параметру | `GetTrackColorSettings` | правила окраски (по статусам или по параметру) |
| Рейсы + отрезки (полная картина) | `GetTrips` | рейсы, отрезки, параметры, итоги |
| Только рейсы, без отрезков | `GetTripsOnly` | легче и быстрее `GetTrips` |
| Только итоги по рейсам | `GetTripsTotal` | агрегаты без детализации |
| Один конкретный тип отрезка | `GetStage` | подмножество `GetTrips` по имени отрезка |
| Значения параметров в каждой точке | `GetTripItems` | таблица «точка × параметр» |
| Табличные данные по рейсам | `GetTripTables` | значения выбранных параметров по рейсам |
| Рейсы с разбивкой по своим геозонам | `GetTripsCustom` | дополнительный отрезок по указанным геозонам |
| Агроучёт: обработанные площади | `GetTripsArea`, `GetTripsGroupByArea`, `GetTripsGroupByDevice` | полигоны и площади полей |
| Мобильные контрольные точки | `GetTripsMobileCheckpoints` | рейсы с МКТ |
| Фотографии с прибора | `EnumPhoto` → `GetPhotoFile` / `GetPhotoZIP` | список и содержимое снимков |

Общие параметры этой группы:

| Параметр | Назначение |
|---|---|
| `IDs` | GUID'ы объектов мониторинга через запятую |
| `SD`, `ED` | начало и конец периода, `yyyyMMdd` или `yyyyMMdd-HHmm` |
| `tripSplitterIndex` | какой делитель на рейсы применять; `0` — по умолчанию, `-1` — не разбивать |
| `tripParams` | список рейсовых параметров; `null` — все |
| `tripTotalParams` | список итоговых параметров; `null` — все |
| `finalParams` | список финальных параметров для онлайн-методов |

> Запрашивайте явные списки `tripParams` / `tripTotalParams` вместо значения по умолчанию:
> у схемы могут быть десятки параметров, и ответ «все параметры» за месяц по сотне машин
> легко вырастает до сотен мегабайт.

## 4. Работа со свойствами

Свойства — это пользовательские атрибуты объектов (госномер, ФИО водителя, тарировочная таблица,
файл, ссылка и т. д.). Раздел «Доступ к свойствам» — самый регулярный в API: **35 методов**
образуют строгую матрицу «операция × тип объекта».

**Пять типов объектов:** ТС (без суффикса), геозоны (`GF`), водители (`Driver`),
инструменты (`Implement`), задачи (`Task`).

**Семь операций:**

| Операция | Шаблон имени | Что делает |
|---|---|---|
| Чтение всех свойств | `Get<Тип>Properties` | все свойства объектов, опционально на момент `at` |
| Чтение одного свойства | `Get<Тип>Property` | одно свойство по имени |
| Чтение таблицы | `Get<Тип>PropertiesTable` | свойства в табличном виде (история значений) |
| Чтение одной таблицы | `Get<Тип>PropertyTable` | одно свойство в табличном виде |
| Запись | `Set<Тип>Properties` | установка и удаление свойств |
| Запись таблицы | `Set<Тип>PropertiesTable` | полная замена таблицы значений |
| Добавление в таблицу | `InsertInto<Тип>PropertiesTable` | добавление значений с сохранением существующих |

Зная правило, можно не искать метод в списке: свойства водителя в табличном виде читает
`GetDriverPropertiesTable`, записывает `SetDriverPropertiesTable`.

**Типы свойств (`RPropType`):**

| Код | Тип | Код | Тип | Код | Тип | Код | Тип |
|---:|---|---:|---|---:|---|---:|---|
| 0 | String | 5 | Memo | 10 | File | 15 | GeoFence |
| 1 | Number | 6 | Color | 11 | ProgressBar | 16 | Driver |
| 2 | Date | 7 | Bool | 12 | Combobox | 17 | Implement |
| 3 | TareTable | 8 | Radio | 13 | FileLink | 18 | Task |
| 4 | Time | 9 | Image | 14 | Device | 19 | CheckDays |

**Удаление свойства** выполняется тем же методом `Set...Properties`: если `Value` отсутствует
или равно `null`, свойство удаляется.

**Историчность.** У каждого значения могут быть `SD` и `ED` — период действия. Методы чтения
принимают параметр `at`: без него возвращается срез на текущий момент, с ним — на указанную дату.
Это позволяет, например, узнать, за каким водителем была закреплена машина три месяца назад.

### 5.1. Ключевые сущности

| Модель | Назначение | Основные поля |
|---|---|---|
| `RSchema` | организация (схема) | `ID`, `Name`, `Group`, `GroupID`, `State` |
| `REnumDevices` | дерево техники | `Groups[]`, `Items[]`, `VirtualTrees[]`, `VirtualTreeAssigned` |
| `RGroupItem` | узел группы | `ID`, `ParentID`, `Name` |
| `RDeviceItem` | объект мониторинга | `ID`, `ParentID`, `Name`, `Serial`, `Allowed`, `Properties[]`, `TripSplitters[]`, `FixedLocation`, `IsAreaEnabled` |
| `ROnlineInfo` | текущее состояние | `LastPosition`, `DT`/`DTLocal`, `State`, `Speed`, `Course`, `Address`, `Final` |
| `RTrackInfo` | трек | параллельные массивы `DT[]`, `Lat[]`, `Lng[]`, `Speed[]`, плюс `Photos[]` и `ColorSettings` |
| `RTrips` → `RTrip` → `RTripStage` | рейсы и отрезки | `SD`/`ED`, `PointStart`/`PointEnd`, `Stages[]`, `Total` |
| `RGeoFence` | геозона | `IsPolygon`, `R`, массивы `Lat[]`/`Lng[]`, `Holes[]`, оформление |
| `RUser` | пользователь | `Login`, `FIO`, `State`, `IDRoles[]`, контакты, `Restrictions` |
| `RParameter` | параметр схемы | `Name`, `Caption`, `Alias`, `Unit`, `Format`, `Expression`, `ReturnType`, `Statuses[]` |
| `RServiceWork` | плановая сервисная работа | остатки по дням/км/моточасам, интервалы, прогнозная дата, стоимость |
| `RServiceMaintenance` | выполненное ТО | дата, ответственный, факт/расчёт по км и моточасам, стоимость |

### 5.2. Особенность формата трека

`RTrackInfo` возвращает не массив точек, а **набор параллельных массивов одинаковой длины**:
`DT[i]`, `Lat[i]`, `Lng[i]`, `Speed[i]` описывают одну точку. Формат экономит трафик,
но требует явной сборки на клиенте:

```javascript
const points = track.DT.map((dt, i) => ({
  dt, lat: track.Lat[i], lng: track.Lng[i], speed: track.Speed[i]
}));
```

### 5.3. Перечисления

**`ReportFormat`** — формат выгрузки отчёта:

| 1 | 2 | 3 | 4 | 5 | 6 | 7 |
|---|---|---|---|---|---|---|
| PDF | Excel2007 | Word2007 | RTF | XPS | ODS | ODT |

**`ColorDefinedBy`** — способ раскраски трека: `0` — параметрами (не поддерживается),
`1` — статусами переключателей, `2` — одним параметром.

**`AllowedUidSettingsType`** — режим разрешённых UID группы: `0` — наследовать с сервера,
`1` — индивидуальный список, `2` — запретить все UID дочерних организаций.

**`RFileResult`** — результат файловых операций: `Ok`, `FileAccessDenied`, `WriteFileError`,
`FileNotFound`, `UnknownError`.

**Тип платёжного документа** (`UpdateBillingPayment.typeID`): `0` — Normal, `1` — Device,
`2` — Correct, `3` — Promise (обещанный платёж), `4` — Repay (погашение обещанного).

**Состояние биллинга устройства** (`UpdateBillingDeviceStates.value`): `0` — Inherited,
`1` — Off, `2` — On.

### Аутентификация

#### `Login`

**Аутентификация и получение токена (в случае, если она включена)**

Метод Login аутентифицирует пользователя по логину/паролю и возвращает токен, который используется во всех последующих запросах. 
В случае успешной аутентификации возвращается строка-токен. 
В случае ошибочной аутентификации возвращается пустая строка и HTTP Status Code = 401.

`GET / POST` `/ServiceJSON/Login`

| Параметр | Тип | Обяз. | Описание |
|---|---|:--:|---|
| `UserName` | `string` | да | Логин |
| `Password` | `string` | да | Пароль |
| `UTCOffset` | `integer(int32)` | — | Смещение от UTC в минутах |

**Ответ:** `Токен авторизации` &nbsp;·&nbsp; коды: 200, 401

### Базовые методы сервиса

#### `GetGeofences`

**Получение информации о геозонах (точки для полигонов и т.д.)**

Возвращает информацию о геозонах (списки точки для полигонов, радиус точки, название, ....)

если ID принадлежит группе - возвращаются ВСЕ её вложенные геозоны с полной иерархией всех нижевложенных групп, сами группы в результирующий набор не попадает
если ID принадлежит элементу - возвращается информация по нему. Допускается смешивание ID элементов разных типов (групп и элементов) в одном запросе.

`GET / POST` `/ServiceJSON/GetGeofences`

Базовые параметры: `session`, `schemaID`

| Параметр | Тип | Обяз. | Описание |
|---|---|:--:|---|
| `IDs` | `string` | — | ID геозон через запятую. Если параметр не задан, используются все геозоны схемы. |

**Ответ:** `object`

#### `GetGeofencesInRect`

**Получение информации о геозонах в определенной области**

Возвращает информацию о геозонах в определенной области.

`GET / POST` `/ServiceJSON/GetGeofencesInRect`

Базовые параметры: `session`, `schemaID`

| Параметр | Тип | Обяз. | Описание |
|---|---|:--:|---|
| `latmin` | `string` | да | координаты области |
| `lngmin` | `string` | да | координаты области |
| `latmax` | `string` | да | координаты области |
| `lngmax` | `string` | да | координаты области |

**Ответ:** `object`

#### `EnumDesignerParameters`

**Получает список параметров**

Возвращает список параметров по одному или нескольким приборам. Приборы, ID которых не найден – в результате отсутствуют.

`GET / POST` `/ServiceJSON/EnumDesignerParameters`

Базовые параметры: `session`, `schemaID`

Пример:

```
{
  "705934C0-7A59-4372-8E08-B6A50D5CA358": [
     "AGDS_0_1_231025_000003_4.jpg",
     "AGDS_0_1_231025_000103_5.jpg",
  ]
}
```

Внимание! Метод GET невозможно протестировать в Swagger из-за передачи параметров в теле запроса(ограничение самого Swagger), но им можно пользоваться из стороннего ПО.

`POST` `/ServiceJSON/GetPhotoZIP`

Базовые параметры: `session`, `schemaID`

**Тело запроса** (`multipart/form-data`): `fileIDs`: `object`

**Ответ:** `Success`

### Изменение объектов

#### `SetGeofences`

**Создает, изменяет или удаляет геозоны**

В теле запроса передается один параметр:
geofences - JSON-сериализованный массив из элементов RGeoFence (см. GetGeoFences).
Для каждого элемента применяются следующие правила:
- если ID отсутствует или Guid.Empty (00000000-0000-0000-0000-000000000000) или такого ID геозоны не найдено в схеме - создается новая геозона в группе с указанным ParentId.
- если Name у геозоны отсутствует - она удаляется. В этом случае все свойства кроме ID игнорируются.
- Holes могут отсутствовать.
- если последняя точка геозоны совпадает с первой (такое получается при конвертации из некоторых геоформатов) - она игнорируется и не сохраняется.
- если тип геозоны точка (IsPolygon==false) и точек передано больше одной - используется только первая.
Если необходимо изменить несколько геозон - предпочтительнее это делать одним запросом, а не для каждой геозоны т.к. после изменения делается перезагрузка геозон в схеме.

`POST` `/ServiceJSON/SetGeofences`

Базовые параметры: `session`, `schemaID`

**Тело запроса** (`application/x-www-form-urlencoded`, `application/json`): `geofences`: `RGeoFence[]`

**Ответ:** `RGeofenceSetResult`
